## [Unreleased]
### Changed
- **All API JSON is now `snake_case`** (migration `014_embed_media_snake_case`): the ticket panel/category/ticket models, clock, translation, guild config, reaction roles, ticket stats and `EmbedMedia` (`iconUrl` becomes `icon_url`) previously mixed camelCase with a few snake_case outliers (`bot_joined`, `role_id`, `discord_client_id`), which is what made reaction-role creation fail with "Invalid Channel ID format" (the dashboard sent `channelId`, the handler read `channel_id`). One casing is now the rule (see CLAUDE.md). The dashboard converts keys at the `fetchJSON` boundary, so its types remain camelCase. **Breaking for any external API client:** every camelCase key is renamed (e.g. `channelId` to `channel_id`, `embedMedia` to `embed_media`, `refreshMinutes` to `refresh_minutes`, `memberCount` to `member_count`). Migration 014 rewrites stored `iconUrl` keys in the four embed-media JSONB columns.
- Reaction role endpoints now return a dedicated response shape (`id`, `guild_id`, `channel_id`, `title`, `description`, `mappings[{emoji, role_id}]`) with string IDs instead of the raw GORM model.

### Added
- **Clock channel refresh interval and guided setup** (migration `013_clock_refresh_interval`): the Clock Channels page is now a three-step wizard (channels, format & timezone, review & save) for one date channel and one time channel sharing a timezone. A new **refresh** dropdown (5, 10, 15, 30 minutes or 1 hour) is stored per clock as `refresh_minutes`; the worker still wakes every 5 minutes and skips a clock until its own interval has elapsed.
- **Clock channels** (new `clock` feature module + migration `012_clock_channels`): channels the bot renames to show the current date or time, e.g. `📅 Saturday Apr 27th` / `🕐 3:17am UTC`. Configured from a new **Clock Channels** dashboard page (first item in Server Management): each clock has a format preset, an optional emoji, and an **IANA timezone chosen from a dropdown that shows the GMT offset and is sorted by it (default UTC)**. An admin picks per clock whether the bot **creates** a view-only voice channel (optionally under a category) or **links an existing** voice channel. A background worker (started beside the ticket auto-close scheduler) renames every clock every 5 minutes and skips unchanged names, since Discord limits renames to about 2 per 10 minutes per channel, so the time can lag a few minutes. New REST routes under `…/guilds/:id/clock-channels` (list/create/update/delete/timezones) and `GET …/discord/voice-channels` for the picker. No slash command. See [TECHNICAL_SPEC.md](file:///d:/Pesronal/Projects/Discord%20Bot/docs/v1/TECHNICAL_SPEC.md) §3.2, §4.10, §8 and [USER_JOURNEY.md](file:///d:/Pesronal/Projects/Discord%20Bot/docs/v1/USER_JOURNEY.md) §5.3, §7.6.
- **Bot connection status + Reconnect in the dashboard** (`/admin/apps`, USER_JOURNEY A.12 — status/reconnect subset): lists each Discord application with a live Connected/Disconnected indicator and a **Reconnect** button (wired to the existing `POST /admin/apps/:id/reconnect`), so a bot whose gateway silently dropped (offline in Discord, servers stuck on "Invite Needed") can be revived without redeploying. Backend: `GET /admin/apps` now returns `connected` (new `Registry.IsConnected`: session ready + heartbeat ACK within 2 min), and `GET /auth/me` returns `is_owner`. A header **Admin** link appears on `/servers` for eligible users.
- **Bot owner is read from Discord; the `OWNER_DISCORD_ID` env var is removed** (`Registry.IsBotOwner`): the owner of a managed Discord application (`GET /oauth2/applications/@me` with the bot's token — `owner`, or `team.owner_user_id` for team apps) is the bot owner, cached 10 min with the last answer kept if Discord is unreachable. `DiscordSessionProvider` gains `IsBotOwner`. **Deployment note:** `OWNER_DISCORD_ID` is no longer read anywhere and can be deleted from Railway.
- **Automatic gateway recovery** (`Registry.RunWatchdog`): a bot session unhealthy for 3 minutes is restarted automatically, then retried with exponential backoff (cap 30 min) so a permanent fault can't hammer Discord's identify limit. Restarts reuse the same session object (close + open in place), and `StartSession` with an unchanged token now does the same, because discordgo's own reconnect loop can reopen a closed session and a second session on one token would process every event twice. A session whose first connect failed stays registered so it keeps being retried, and slash commands are (re)registered after the first successful connect. Fixes a bot that silently dropped its gateway connection and stayed offline until a manual restart.
- **Starting, stopping, and restarting a bot is bot-owner only** (`OwnerMiddleware`): `POST /admin/apps`, `PUT /admin/apps/:id`, `DELETE /admin/apps/:id` and `POST /admin/apps/:id/reconnect` now return 403 to anyone but the bot owner. A bot is a single gateway connection shared by every server, so a server administrator must not be able to take it down for all of them. Administrators of a server with the bot keep read-only access to status (`GET /admin/apps`), and the dashboard hides Reconnect from them.
- **Admin access rule tightened:** `AdminMiddleware` previously admitted any user with a non-empty `managed_guilds` (which includes anyone who can manage *any* server, even without the bot). It now admits only the bot owner, or the owner/`ADMINISTRATOR` of a guild where the bot is installed. `managed_guilds[]` gains `is_admin`; existing sessions pick it up on the next `/auth/refresh` (the servers page does this on load). **Behavior change:** Manage-Server-only users lose access to `/admin/apps/*` (nothing in the dashboard used it).
- **Message auto-translation** (new `translation` feature module + migration `010_translation_config`): a per-guild feature that translates member messages via a pluggable engine. Two configurable triggers — **auto** (every message in admin-selected channels) and **reaction** (when a member reacts with one of the guild's configured trigger emojis) — each with its own enable toggle behind a master on/off switch. The translation **engine (DeepL / Google Cloud Translation / self-hosted LibreTranslate) and its API key are chosen per-guild from the dashboard**, in the same tab; the key is stored **AES-256-GCM encrypted** (reusing `TOKEN_ENCRYPTION_KEY`) and masked as `***` on read, mirroring the `discord_apps` credential pattern. Target language resolves per-item override → per-guild default → the existing `guilds.language` → `en`; messages already in the target language (or pure links/mentions/emoji) are skipped, and translations post as an embed reply. New engine abstraction `internal/pkg/translate` (`Translator` interface + `NewTranslator` factory), REST routes under `…/guilds/:id/translation` (config `GET`/`PUT`, channel and trigger-emoji add/remove), gateway hooks on `MessageCreate`/`MessageReactionAdd`, and a **Message Translation** dashboard screen under Server Management.
- **Emoji picker (unicode + custom server emoji)** across the dashboard: a shared `EmojiPicker` component with a "Standard" tab (curated, searchable unicode set) and a "Server" tab listing the guild's own custom emoji, wired into the **Ticket Panels** (per-category button emoji) and **Reaction Roles** (mapping emoji) screens; an `EmojiView` helper renders custom emoji as CDN images everywhere they're previewed. New `GET …/guilds/:id/discord/emojis` endpoint (served from the gateway `State` cache, so Discord's `GUILD_EMOJIS_UPDATE` events keep it fresh without a REST call; frontend adds a 5-min TTL cache). Shared `discordutil` helpers (`ParseComponentEmoji`, `ReactionEmojiAPIName`, `CustomEmojiMention`/`URL`) normalize the three emoji representations Discord needs — button/select `ComponentEmoji`, reaction-endpoint `name:id`, and the picker's canonical `<:name:id>`/`<a:name:id>` mention form — so custom emoji render on ticket buttons and reaction-role reactions grant/revoke correctly. Also fixes reaction-role mappings never being persisted from the dashboard in non-demo mode (the create flow now calls the per-emoji endpoint).
- **Emoji in free-text fields**: an insert-at-cursor `EmojiInsertButton` (compact smiley trigger sharing the same combined unicode + server-emoji panel) is wired into the message-content and embed-**description** fields where Discord actually renders custom emoji — **Welcome** DM body, and **Ticket Panels** panel content/embed description + per-category opening content/description. Emoji are spliced at the caret (replacing any selection) rather than overwriting the field, and the panel live previews now render inserted custom emoji as images via a new `EmojiText` helper. Titles/author/footer are intentionally excluded since custom emoji don't render there.
- **Ticket "Resolve" status** ([TECHNICAL_SPEC.md](file:///d:/Pesronal/Projects/Discord%20Bot/docs/v1/TECHNICAL_SPEC.md) §6, §4.5; [COMMAND_REFERENCE.md](file:///d:/Pesronal/Projects/Discord%20Bot/docs/v1/COMMAND_REFERENCE.md)): a new `resolved` ticket status, distinct from `closed` — staff mark a ticket as handled via a `Resolve` button (alongside the existing Claim/Close) or `/ticket resolve`, without locking the channel or generating a transcript. Resolving (re)starts an auto-close timer using the category's existing auto-close window, so an unanswered resolved ticket closes itself; un-resolving reverts to Open/Claimed and clears the timer. New `POST …/tickets/:id/resolve` and `.../unresolve` endpoints, `ticket_status` enum gains `resolved` (migration `008_ticket_resolved_status`), and the dashboard Tickets page gets a matching filter tab, badge, and row actions.

### Changed
- **Resolved all 8 open questions in USER_JOURNEY.md §14** (now retitled "Decisions Log"), and propagated each into the spec:
  1. **Demo mode** gated behind an explicit `/demo` route; the mock-fallback is removed from `lib/api.ts` for real sessions — no silent mock rendering on API failure.
  2. **Ticket detail** is a full route (`/tickets/[id]`), not a drawer.
  3. **Sidebar regroup:** CONFIGURE → **"Server Management"** (Ticket Panels, Welcome incl. auto-roles, Reaction Roles); **Settings** (General, Staff & Access) stays a separate group for bot/server-level plumbing. Bot-wide status/error-logs across every server it's in is noted as a future `/admin/apps` extension, out of scope for now.
  4. **Staff (Level 2)** sidebar: Server Management + Settings groups are **fully hidden**, not read-only.
  5. **Overview stats:** counts + avg. resolution only for v1; sparkline/chart deferred to "Dashboard v2."
  6. **Invite permissions:** scoped permission integer (View/Manage Channels, Manage Roles, Manage Threads, Send Messages, Embed Links, Read Message History, Add Reactions, Use External Emojis, Manage Messages) replaces `permissions=8` (Administrator).
  7. **Ticket detail conversation is read-only in v1** — no dashboard reply composer, no `POST …/tickets/:id/messages` endpoint. Staff reply in the Discord thread.
  8. **Participants (`S-05`) deferred** — the `ticket_participants` table and its 3 endpoints are dropped from v1; per-category support roles (`ticket_categories`, multi-role) already auto-grant every role-holder access to a ticket's thread, covering the real workflow.
  
  Net effect on [Appendix B](file:///d:/Pesronal/Projects/Discord%20Bot/docs/v1/USER_JOURNEY.md#appendix-b--data-contract--endpoint-coverage): the journey's new backend surface shrinks from "6 endpoints + 1 table" to **4 endpoints + 0 new tables**. ## [1.1.0] - 2026-06-21
### Added
- **`bot_settings` singleton table** (`migrations/002_bot_settings.up.sql`): Stores all four Discord credentials (`DISCORD_TOKEN`, `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `DISCORD_REDIRECT_URI`) encrypted at rest with AES-256-GCM. Eliminates the need to update Railway environment variables when credentials change.
- **`internal/app/settings/` vertical module**: Full model / repository / service / handler stack following the established vertical module pattern.
- **Admin REST API endpoints** (`GET`, `PUT /api/v1/admin/settings`, `POST /api/v1/admin/settings/reconnect`): Dashboard-facing CRUD for bot credentials. Token and client secret are always masked in GET responses.
- **Live bot reconnect** (`bot.Reconnect()`): Updating the token via `PUT /api/v1/admin/settings` automatically closes and reopens the Discord Gateway connection on the same `*discordgo.Session` pointer — no restart required, all handlers preserved.
- **`internal/api/middleware/admin.go`**: Admin-only middleware that checks `managed_guilds` JWT claim or `OWNER_DISCORD_ID` env var override.
- **`OWNER_DISCORD_ID` env var**: Optional; grants a specific Discord user unconditional access to the admin settings endpoints.
- **First-boot seeding**: On startup, if `bot_settings` is empty and `DISCORD_*` env vars are set, credentials are automatically encrypted and persisted to the DB. After first boot, env vars can be safely removed from Railway.

### Changed
- **`internal/config/config.go`**: All four `DISCORD_*` environment variables changed from required (`mustGetEnv`) to optional (`getEnv`). Added `HasDiscordSeed()` helper and `getEnvFallback()` for Railway's `PORT` precedence.
- **`cmd/shrimpy/main.go`**: Startup sequence reordered — `bot_settings` table migrated first, credentials seeded/loaded from DB, Discord session constructed from DB token, then remaining modules built.
- **`internal/app/auth/handler/handler.go`**: Auth callback now fetches OAuth2 credentials from the settings service (30s cached DB lookup) instead of from startup config.
- **`internal/api/server.go`**: Admin route group added under `/api/v1/admin/`.
- **`railway.toml`**: `healthcheckTimeout` increased from 10s to 30s to accommodate cold-start DB connection + migration time.
- **Technical Spec** ([TECHNICAL_SPEC.md](file:///d:/Pesronal/Projects/Discord Bot/docs/v1/TECHNICAL_SPEC.md)): Updated sections 3 (schema), 4 (API), 8 (directory structure), 9 (config), 10.2 (Railway vars), 10.4 (Vercel vars), 10.5 (docker-compose).

### Fixed
- **Railway health check failure**: HTTP server now starts before the Discord Gateway connection so `/health` is reachable during Railway's health check window.
- **Railway `PORT` env var**: Config now reads Railway's injected `PORT` variable first, falling back to `API_PORT`, then `8080`.
